# Manage Code Review

## 目的

コードを変更せず、再現可能で修正に直結する指摘を重大度順に提示する。

## 使用条件

- ユーザーがレビュー、監査、差分評価だけを求めている。
- PR、commit、branch、working tree、指定ファイルが対象である。

## 使用しない条件

- 修正まで明示されている場合は、レビューを完了してから `manage-code-change` へ進む。
- 見た目中心の画面監査や原因不明の症状調査には使用しない。

## 事前確認

1. 対象差分と比較元を確定する。working treeでは既存の未追跡ファイルも対象か確認する。
2. ユーザー要求、`AGENTS.md`、関連Skill、実装、テスト、API・設計文書を読む。
3. 変更行だけでなく呼び出し元、データ保存、出力、テストを確認する。
4. レビューのみなのでファイルを編集しない。

## 手順

1. 差分を機能単位に分け、要求との対応を作る。
2. 次の観点を順に確認する。
   - 正しさ、境界値、空値、0とnull、長い文字列、重複入力
   - エラー処理、HTTP status、部分失敗、ログ、例外の可視性
   - 状態遷移、Undo/Redo、再描画、非同期競合、古いレスポンス
   - SQLite制約、移行、Import/Export、API・データ互換性
   - 認証、管理者権限、入力検証、secret・個人情報の露出
   - 性能、N+1 query、不要な再取得、DOM全再描画、メモリ・リソース解放
   - キーボード、focus、responsive、light/dark、Gantt/Member Load parity
   - テストの失敗経路、回帰範囲、実装に追従しただけの弱いassertion
   - 無関係な変更、生成物、依存・ビルド設定の不要変更
3. 候補ごとに実際の到達経路とユーザー影響を確認し、推測だけの指摘を落とす。
4. 必要な場合だけ非破壊のテスト・buildを実行し、実行範囲を記録する。
5. 問題がなければ、確認範囲と未確認範囲を明記する。

## 重大度

| 重大度 | 基準 |
|---|---|
| Critical | データ損失、権限逸脱、起動・ビルド不能、主要操作の破壊 |
| Major | 通常操作の誤動作、互換性破壊、重要な回帰、実質的なテスト欠落 |
| Minor | 限定条件の不具合、保守性低下、局所的なUX・文書不整合 |

好みだけの指摘や既存コード全体の問題は、対象差分が悪化させない限りfindingにしない。

## 検証

- 各findingにファイルと最小の行範囲、発生条件、影響、根拠を付ける。
- 到達不能な経路や既存テストで否定される仮説を指摘しない。
- テストを実行した場合はコマンドと結果を、未実行ならその旨を示す。

## 禁止事項

- レビューのみの依頼でコード、文書、設定を変更しない。
- 根拠なく「セキュリティ上危険」「性能が悪い」と断定しない。
- 重大度を水増ししない。
- findingより先に長い要約を置かない。

## 完了報告

1. findingを重大度順に、ファイル・行・影響・根拠つきで示す。
2. 次に確認した範囲、実行した検証、未確認範囲を示す。
3. findingがない場合は明言し、残存するテスト・画面・環境上の限界を示す。
