# Manage Code Change

## 目的

要求を満たす最小の変更を、既存設計・データ契約・UI契約を保ちながら実装する。

## 使用条件

- 機能追加、修正、リファクタリング、文書更新を依頼されている。
- 原因または期待動作が十分に確定している。
- リポジトリ変更が依頼の範囲に含まれる。

## 使用しない条件

- 調査のみ、原因特定のみなら変更しない。
- レビューのみなら変更しない。
- UI実装は本Skillに加えて `manage-ui-design`、CSVは `manage-csv-export` を使用する。

## 事前確認

1. `git status --short` と `git diff --stat` で既存差分を把握する。
2. 要求を観測可能な受け入れ条件へ変換する。
3. `AGENTS.md` のアーキテクチャ要点と対象設計書を使い、入口、呼び出し元、依存先、永続化、出力を確認する。
4. 類似実装、共通ユーティリティ、既存テストを `rg` で検索する。
5. 変更対象にユーザー差分がある場合は、内容を読み、上書きせず外科的に編集する。

## 手順

1. 変更する動作、変更しない動作、互換性条件を明文化する。
2. 定義から呼び出し元と出力先をたどり、最小ファイル集合を決める。
3. 修正前に再現テストまたは既存テストの期待を確認する。
4. 複数利用箇所が既にある場合だけ共通化する。単一用途の新規抽象化を作らない。
5. 既存命名、API wrapper、CSS変数、dialog/toast、serviceを再利用して実装する。
6. 動作変更に対応するテストを追加・更新する。テストを実装へ合わせる前に、要求と既存契約のどちらが正しいか確認する。
7. `docs/DocumentationOperations.md` に従い、API、設計、手順、ユーザー操作、テスト文書を必要な範囲だけ更新する。
8. `manage-build-and-test` で狭い検証から広い検証へ進む。
9. `git diff --check` と対象差分を読み、無関係な整形、生成物、デバッグコード、秘密情報がないか自己レビューする。

## 変更種別ごとの注意

| 種別 | 必須確認 |
|---|---|
| Model | 起動時移行、既存SQLite、to_dict、Import/Export、API、pytest |
| API | auth decorator、validation、status/error、`api.js`、呼び出し元、API文書 |
| Allocation | 0とnull、一意キー、Undo/Redo、3画面、export |
| Shared state | localStorage default、CustomEvent、保存ビュー、全購読画面 |
| UI | DOM hook、キーボード、busy/save状態、desktop/narrow、light/dark |
| Docs only | コマンド・パス・リンクを実体と照合。コードは変更しない |
| Refactor | 変更前後の外部動作を固定するテスト。公開契約を増減しない |

## 検証

- 最も狭い関連テストを先に実行する。
- backend変更は関連pytest、frontend変更は関連Vitestを実行する。
- 広いfrontend変更はlint、format出力確認、`npm run build` を行う。
- UI変更は実画面、API/model変更は関連文書と互換性を確認する。
- 実行できない検証は、理由と代替証拠を示す。

## 禁止事項

- 範囲外の問題を便乗修正しない。重大な問題は最終報告へ分離する。
- 不要な互換レイヤー、ハードコードの暫定回避、重複API wrapperを追加しない。
- 無関係なformat、依存更新、ビルド・CI変更、公開API変更を行わない。
- 例外を握りつぶさず、既存のerror/toast契約を使う。
- 自動生成物、DB、secret、監査出力を変更対象にしない。

## 完了報告

- 受け入れ条件に対する実装結果を要約する。
- 変更ファイル、テスト、ビルド、画面確認、文書更新を示す。
- 未実施検証、互換性・移行・性能・セキュリティの残存リスクを示す。
