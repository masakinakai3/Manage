# Manage Bug Investigation

## 目的

確認済み事実と仮説を分離し、症状から原因箇所まで再現可能な証拠でたどる。

## 使用条件

- 原因不明の不具合、テスト失敗、ビルド失敗、性能低下を調べる。
- 環境差、入力データ、直近変更、非同期状態を切り分ける。
- 修正前に再現条件と回帰テスト候補が必要である。

## 使用しない条件

- 原因が確定し修正のみを求められている場合には使用しない。
- 差分レビューだけ、または見た目の監査だけの依頼には使用しない。

## 事前確認

記録する:

- 症状、期待動作、実際の動作
- 再現手順、再現率、初回発生時期、影響範囲
- 入力データ、ユーザー権限、期間・scale・filter、画面幅、light/dark
- Python/Node/ブラウザ/EXEか開発版か、DBの場所
- 直近差分、ログ、console、network response、失敗testの完全な出力

`git status --short` と関連履歴を確認し、ユーザーの未コミット差分を原因候補から除外しない。

## 手順

1. 最小再現を作る。再現できない場合は、観測できた条件とできなかった条件を残す。
2. `manage-architecture` を使い、UI -> API -> route -> model/service -> SQLite、またはbuild入力 -> 出力の経路をたどる。
3. 仮説を列挙し、各仮説に反証可能な確認方法を付ける。
4. ログ追加や一時変更より先に、既存ログ、test、network、DB query、`git diff` から証拠を集める。
5. 仮説を一つずつ検証し、否定した仮説も簡潔に記録する。
6. 原因を、症状が起こる入力から観測結果まで説明できる粒度に絞る。
7. 修正候補と再発防止テストを示す。ユーザーが調査だけを依頼した場合は実装しない。
8. 修正も依頼されている場合は `manage-code-change` へ進み、修正前に失敗するテストまたは再現証拠を保持する。

## よく壊れる境界

- `allocation_rate` の0とnull、月文字列、同一配賦キー
- Gantt / Member Load / Insights間の期間・scale・filter同期
- local rerenderとAPI再取得、古い非同期レスポンス、Undo/Redo
- Themeの旧互換マイルストーン列と `theme_milestones`
- admin-only export/importと一般ユーザーUI
- 開発版 `frontend/dist`、dev onedirの外部dist、release onefileの同梱dist
- 既存SQLiteに対する起動時移行

## 性能低下の調査

`Requirement.md` の標準規模はメンバー50名以下、テーマ200件以下だが、数値付きの合格時間とベンチマークは存在しない。性能改善を主張する場合:

1. 固定データ、同じ環境、同じ操作、同じbuildを使用する。
2. ウォームアップ後に5回以上測定し、中央値と範囲を記録する。
3. frontendはnetwork回数、render回数、処理時間を、backendはrequest時間とquery/集計箇所を測る。
4. 必要に応じてプロセスメモリを同条件で比較する。
5. 最悪ケースと通常ケースを分け、変更前後で正確性テストも実行する。
6. ベースラインが取れない場合は「改善した」と断定せず、ボトルネック候補として報告する。

## 検証

- 原因候補を再現する最小テストまたは観測手順を示す。
- 修正した場合は、修正前の失敗と修正後の成功、関連回帰テストを示す。
- 類似コードを `rg` で検索し、同じ原因が他画面・routeにないか確認する。
- 実行不能なbrowser、EXE、環境差は未確認として残す。

## 禁止事項

- 再現できない症状を推測だけで断定しない。
- UI上の値をハードコードしてbackend/dataの原因を隠さない。
- DB削除、test削除、基準緩和、warning無効化を修正としない。
- 調査のみの依頼でリポジトリを変更しない。
- 性能測定条件やデータ量を途中で都合よく変えない。

## 完了報告

- 確認済み事実、原因、証拠、否定した主要仮説を示す。
- 再現条件、影響範囲、修正候補、回帰テスト候補を示す。
- 未確認事項と追加で必要な入力・環境を示す。
